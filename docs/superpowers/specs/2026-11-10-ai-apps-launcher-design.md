# AI 应用页（内置进程分流 + 启动器）设计

日期：2026-11-10
状态：草案，待用户审阅

## 1. 意图

新用户装好 Routa 后，最常见的诉求是"让 ChatGPT / Claude / Cursor 能用"。现在要做到这一点，得先理解进程分流、知道进程名、自己建规则、再回首页确认代理开着、再去开始菜单打开应用。门槛太高。

这个功能把常见 AI 应用做成内置的、像启动器一样的卡片：选个节点，点"启动"，剩下的都由 GUI 自动完成。**越简单越好**，这是用户提出的首要原则。

## 2. 目标 / 非目标 / 反目标

**目标**
- 新用户从打开 AI 应用页到"应用已在代理下运行"，最多两次点击（选节点 + 启动）。
- 应用列表远程拉取，加新应用不用发版本。
- 第一版内置 ChatGPT、Claude、Cursor 三个应用。

**非目标**
- 带宽测速（只测延迟）。
- 让用户在 AI 应用页添加任意自定义应用，或编辑内置应用的进程列表。
- macOS / Linux（项目目前只面向 Windows）。
- 简洁版（`SimpleLayout`）不加 AI 应用入口。用户未来会移除简洁版。
- 开机自动启动这些应用。

**反目标（即使能跑，做成这样也算失败）**
- 卡片上堆满文字。卡片要非常简洁。
- AI 应用的规则出现在"进程分流"规则列表里。两边必须完全分开。
- 远程列表能让 GUI 运行任意命令或任意程序。
- 每次开启、换节点、关开关都弹确认框，把用户烦死。

## 3. 用户已确定的部分

### 3.1 入口
左侧菜单在"进程分流"**上面**新增"AI 应用"一项（`src/components/Layout.tsx` 的 `pages` 数组）。

### 3.2 页面布局：启动器卡片网格（用户选定方案 B v2）
每张卡片只有这些元素：
- 应用图标（大）
- 应用名称
- 一行：节点下拉框 + **延迟数字**（点击重测） + 代理开关
- 一个主按钮
- 右上角小圆点：代理生效中显示绿色。不用文字表示状态。

| 状态 | 外观 | 主按钮 |
|---|---|---|
| 未安装 | 整卡置灰，没有节点和开关 | 显示"未安装 · 下载"链接，打开官网（链接来自远程列表） |
| 已安装、未运行 | 正常 | "启动" |
| 已安装、运行中 | 正常 | "运行中"，点击后把该应用窗口切到最前面 |

页头右侧放"进程分流"总开关（与进程分流页的总开关是同一个 `ProcessRouting.enabled`）。

### 3.2.1 总开关关闭时：用颜色和状态表示，不用文字（用户选定方案 A"整页褪色"）
- 各应用开关**保留各自状态**；总开关重新打开后，之前开着的应用自动恢复（和进程分流规则行为一致）。
- 已安装卡片的图标、节点下拉框、延迟变成黑白半透明。
- 原本开着的开关变成浅色，表示"记住了，但暂停中"。
- 小圆点全部为灰色。
- 页头总开关带一圈淡蓝色光晕，引导用户去点。
- "启动"按钮保持蓝色可点。点"启动"或拨动任意应用开关，按 3.5 顺带打开总开关。
- 不显示横幅或提示文字。只在鼠标悬停到浅色开关上时，出现一行小提示。

### 3.3 节点
- 每个应用各自选择节点，互不影响，也不跟随首页的当前节点。
- 打开开关时使用该应用自己的节点。

### 3.4 代理开关
- 打开：该应用的所有进程立即走它的节点；关闭：立即恢复。
- 规则只在 AI 应用页管理，不出现在"进程分流"页。

### 3.5 启动按钮（启动器）
点击"启动"时，GUI **自动**（不询问）准备好所需的一切，然后打开应用：
1. 内核没运行就启动内核。
2. 分流服务（routa-procsvc）没安装就安装（只弹一次 UAC，沿用现有流程）。
3. "进程分流"总开关（`ProcessRouting.enabled`）没开就打开。AI 应用规则**受总开关控制**：总开关关闭时，所有 AI 应用规则都不下发（用户决定）。
4. 该应用开关没开就打开（如果需要冲突确认、节点选择，见下文）。
5. 等服务确认规则已经生效。
6. 启动应用。

### 3.6 与进程分流规则冲突
开启某个 AI 应用时，如果"进程分流"页已有规则包含该应用的进程：
- 弹框提示冲突，说明是哪条规则里的哪个进程。
- 用户确认后，**只从那条规则里删除冲突的进程**，规则里其他不相关的进程不动。
- 如果那条规则只剩冲突的进程，就整条删除，弹框文案改成"将删除该规则"。
- 用户取消则不开启。

### 3.7 断开旧连接
- 开启时如果应用已经在运行，弹框提示"会断开 X 的现有连接，让它重新连到代理"。
- 弹框带"下次不再提示"勾选框。勾选后以后直接断开、不再弹框（全局一个偏好，设置页里可以恢复）。
- 应用没在运行时直接开启，不弹框。
- 实现上复用分流服务已有的 `Op::Reset`（`reset_on_change`，`procsvc/src/reconcile.rs`）：AI 应用生成的规则一律 `reset_on_change = true`。注意现在只断 IPv4 TCP。

### 3.8 延迟
- 卡片上显示当前节点的延迟，点击重测。只测延迟，不测带宽。

### 3.9 出错时直连还是断网：由远程配置决定
- 远程列表里每个应用带 `on_fault`（`direct` / `block`），AI 应用规则使用这个值。缺省为 `block`（我的决定：AI 服务封地区，泄露真实 IP 可能导致封号）。
- `procroute::decide` 现有的强制断网情况不变：没选节点、节点失效、内核非手动停止、FailClosed 时，一律断网，与 `on_fault` 无关。`on_fault` 只作用于现有逻辑中本来就看 `on_fault` 的那些情况（内核崩溃、启动中、恢复中、手动停止）。
- 退出提示（`exit_needs_confirm`）和 WFP 守护也沿用现有逻辑，按规则最终的动作决定。

### 3.10 换节点、关开关时也断开旧连接（用户选定方案 B：改分流服务）
- 现状：服务只在动作种类（Proxy / Direct / Block）变化时 `Reset`（`procsvc/src/reconcile.rs` 第 9 条）。所以开着开关换节点（Proxy→Proxy），或者关开关（规则被删除）时，已有连接不会断开。
- 改为：设置了 `reset_on_change` 的规则，以下两种情况也执行 `Reset`：
  1. 动作仍是 Proxy，但代理目标变了（换节点）；
  2. 规则被删除（关开关）。
- 这条改动对普通进程分流规则同样生效：开了 `reset_on_change` 的普通规则换节点时也会断开。用户认可这种一致性。
- 发布：提升 `PROTO_VERSION`，让老服务被识别为 `NeedsUpdate`，走现有的重装流程（老用户点一次 UAC）。新用户没有影响。（提升版本号是我的决定，目的是确保老服务一定会被替换。）
- 交互：换节点或关开关时，如果应用正在运行，弹 3.7 的同一个"断开旧连接"提示，沿用同一个"下次不再提示"偏好。

### 3.11 GUI 启动时
- 只要有任何一个 AI 应用的开关是开着的，GUI 启动时就自动启动内核，不受 `auto_connect` 偏好影响，避免"重启后 ChatGPT 上不了网"。

## 4. 我（Claude）做的决定，用户可推翻

- **首次选节点：** 应用还没选过节点就打开开关或点启动时，先弹节点选择器，选完记住。
- **按应用的测速地址：** 延迟用每个应用自己的服务地址测（ChatGPT 测 chatgpt.com，Claude 测 claude.ai），地址写在远程列表里，不用全局的 `delay_test_url`。原因是 AI 服务经常封某些地区的节点，用应用自己的地址测才能看出"能不能用"。现有的 `test_delays` 只用全局地址，需要一个带 URL 参数的变体；结果缓存按（节点, URL）区分。节点选择器里的延迟也用这个地址。
- **未安装显示下载链接。**
- **远程列表来源：** 和更新清单一样从 GitHub 拉取，依次尝试直连、`gh-proxy.org`、`ghfast.top`（复用 `src-tauri/src/updater/download.rs` 的 `MIRRORS`）。文件放在仓库主分支（例如 `presets/ai-apps.json`，用 raw 地址），改列表不用发版本。安装包里自带一份兜底，另外缓存最后一次成功拉取的版本。拉取时机：启动时一次，之后每天一次。
- **自动开代理不改用户的接管模式：** "自动打开"只指内核和分流服务，不切换系统代理 / TUN 模式。进程分流本来就不依赖 TUN。
- **反向冲突：** 某个 AI 应用开启过（规则已存在，开或关都算）时，用户在进程分流页新建或编辑规则、加入同一个进程，校验会直接拒绝，提示"已由 AI 应用管理"。和 3.6 合起来，同一个进程任何时刻只归一边管。（实施计划阶段收紧：借用现有的"同一进程只能属于一条规则"校验。）
- **退出 GUI 时：** AI 应用规则和普通进程规则一样处理（沿用现有的 `exit_prompt` 行为）。
- **出错状态：** 节点不可用、服务未确认等情况，小圆点变红，悬停显示原因（复用 `decide` 返回的原因文案）。
- **简洁版遗留的托管规则：** 用户从简洁版切到完整版后，`process_routing` 里可能留有简洁版的托管规则（`managed_rules`）。冲突处理时把它们当普通规则对待，同时把对应 id 从简洁版的 `managed_rules` / `selected_apps` 里同步移除，避免状态对不上。
- **切到前台的实现：** 先找该进程的顶层可见窗口，还原并置前；找不到（比如应用只在托盘）就再启动一次。这三个应用都是单实例的，再启动一次会把已有窗口唤出来。

## 5. 安全边界

远程列表**只能描述**：应用 id、名称、图标、官网下载链接、测速地址、怎么在本机识别它（商店包族名 / 已知安装路径模式 / 卸载注册表项等）、它有哪些进程（第一版只支持进程名，不能带路径；`node.exe`、`python.exe` 这类通用进程名不收录）。

- 列表里**不能有**任意命令行、任意参数、任意 exe 路径。
- 真正启动的，必须是在本机按识别规则实际找到的程序：普通 exe 通过 shell 启动；商店应用通过 AUMID 激活。
- 第一版只按进程名匹配，列表里不出现任何路径；安装路径只用于检测和启动，且只能位于 `%LOCALAPPDATA%`、`%PROGRAMFILES%`、`%PROGRAMFILES(X86)%`、`%APPDATA%` 之下。
- 下载链接只交给系统浏览器打开。
- 列表带 `schema_version`，客户端不认识的版本就忽略远程、用缓存或兜底。

第一版不对列表签名，靠以上约束兜底。

## 6. 约束与现有能力

- 平台：只有 Windows（NSIS 安装包）。
- **可直接复用：**
  - 进程规则的模型和下发链路：`ProcessRule` / `ProcessEntry`（`src-tauri/src/model/types.rs`），`procroute::decide`，`Syncer::push`，隐藏 SOCKS 监听器（`model/hidden.rs`）。改动实时生效。
  - 服务安装和提权：`procroute/elevate.rs`。
  - 内核启停：`Runtime::restart_core`。
  - 运行中的进程列表：`procroute/processes.rs`。
  - 商店应用路径重映射：`procroute/store.rs`。
  - 延迟显示组件：`components/ProcessNodeSelect.tsx`、`DelayText.tsx`。
  - 等服务确认的桌面层包装：`desktop.rs`。
- **需要新做：**
  - 检测应用是否已安装、装在哪。
  - 获取图标（来自列表；拿不到再从本机 exe 提取，由实现者决定）。
  - 启动普通 exe 和商店应用。
  - 把窗口切到前台。
  - 远程列表的拉取、缓存和兜底。
  - 按 URL 测延迟。
- **启动权限注意：** GUI 可能以管理员身份运行（TUN 模式会用 `relaunch.rs` 提权重启）。被启动的 AI 应用**不能**继承管理员权限，必须以普通用户权限启动（例如通过 explorer / shell 激活）。

## 7. 留给实现者

- 远程列表的具体 JSON 结构（满足第 5 节）。
- 三个应用的具体识别规则和进程清单：需要在真机上核实。ChatGPT 是商店应用；Claude 和 Cursor 的安装方式、子进程（Electron 子进程、Cursor 的语言服务器等）都要逐个确认，确保"应用的所有进程"都被覆盖。
- AI 应用规则的存储：实施计划决定放在 `process_routing.rules` 里，用 `ai_app` 字段标记，以复用现有的 decide、隐藏监听器和守护逻辑；界面上仍然完全分开。
- 已安装状态的刷新时机（进入页面、窗口获得焦点、商店包事件等）。
- 卡片的视觉细节，要跟现有 MUI 风格一致。
- 测试策略。
