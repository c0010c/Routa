## 1. 为什么做

节点挂了用户往往要等到上网出问题才发现。现有「自动测速」只把延迟写进节点卡片，用户不盯着界面就不知道。节点监测：按固定间隔探测用户关心的节点，节点变得不可用时发 Windows 系统通知，恢复时再通知一次。

## 2. 目标、非目标、反目标

**目标**
- 用户可开关监测，可配置：监测范围、探测间隔、连续失败几次算不可用、延迟上限、恢复时是否通知。
- 节点从可用变不可用时发一条系统通知；恢复时（若开启）再发一条。
- 点击通知打开 Routa 并定位到该节点。
- 在设置页能看到上次探测结果和每个被监测节点的状态，能手动「立即探测」。
- 在节点页能直接把一个节点加入 / 移出监测，并在卡片上看到监测标记。

**非目标**
- 不做历史记录、可用率统计、图表。
- 不做自动切换节点（故障转移已由 mihomo 的 Fallback / UrlTest 组负责）。
- 不做邮件 / Webhook / 声音等其它通知渠道。
- 不做每个节点单独的间隔或阈值，所有监测节点共用一套参数。
- 简洁模式（Simple）下不显示监测设置和卡片菜单项（见 7.3）。

**反目标（做到了也算失败）**
- 刷屏：节点持续不可用时每个周期都弹通知；或本机断网时每个节点各弹一条。
- 偶发一次超时就报警（默认阈值必须能吸收单次抖动）。
- 内核没运行、正在重启、配置刚变更时报「节点不可用」。
- 监测探测拖慢或阻塞节点切换、配置应用等用户操作。

## 3. 用户可见行为

### 3.1 设置 › 网络与内核 ›「节点监测」分区

位置：紧跟在「测速」分区之后。使用现有 `Section` / `Row` 组件，每项改动即时保存（与「自动测速」一致，用 `SaveFeedback`）。

| 行 | 控件 | 选项 / 说明 | 默认 |
|---|---|---|---|
| 节点监测 | Switch | 描述：「定时探测节点，不可用时发送系统通知」。关闭时下面各行和 footer 都隐藏。 | 关 |
| 监测范围 | Select | 「正在使用的节点」/「指定节点」。前者描述：「代理和进程分流当前使用的节点，随配置自动变化 · N 个」；后者描述「N 个节点」，并在行下方显示现有的 `MemberPicker`（label「选择节点或整组」），可选单个节点或整组（订阅 / 自建组）。 | 正在使用的节点 |
| 探测间隔 | Select | 10 秒、30 秒、1 / 3 / 5 / 10 / 30 分钟、1 小时（最低 10 秒） | 5 分钟 |
| 判定为不可用 | Select | 「失败 1 次即通知」/「连续失败 2 / 3 / 5 次」；描述：「连续失败达到次数才通知，避免偶发抖动误报」 | 连续失败 2 次 |
| 延迟上限 | 数字输入 + 后缀 ms | 空 = 不限；描述：「超过上限也算异常；留空只检查能否连通」。范围 1–60000，非法值显示错误不保存。用户可清空。 | 1000 ms |
| 恢复时通知 | Switch | 描述：「不可用的节点重新连通后再通知一次」 | 开 |

**从「正在使用」切到「指定节点」**时，若指定列表为空，用当前「正在使用」的节点预填，避免切过去是空的。换算规则（这里和 3.2 的加入 / 移出共用）：有 `node` 的 target 换成对应的单节点 `ExitMember`（多条路径的同一节点只留一个，之后按节点自己的代理名探测、不再经过出口网卡）；自动组出口的 target（`node = None`）没法用 `ExitMember` 表示，直接去掉，并用现有的 Snackbar 提示「自动选择的出口「{出口名}」不能加入指定节点，已不再监测」。

**Footer**（灰底，与「内核」分区 footer 同风格）：
- 第一行：「尚未探测」或「上次探测 HH:mm · 下次 HH:mm · N 正常 · M 不可用」（不可用部分红色），右侧「立即探测」按钮（探测中显示「探测中…」并禁用；没有监测节点时禁用）。
- 下面列出被监测节点：状态点 + 节点名 + 次要信息 + 状态文字。
  - 次要信息：「正在使用」范围下是使用者（如「工作代理 :7890」「进程分流 · 微信」），「指定节点」范围下是来源（订阅名 / 手动）。
  - 状态：灰点「等待探测」；绿点「48 ms」；黄点「失败 1/2」（失败未达阈值）；红点「不可用 · 超时」或「不可用 · 延迟 1280 ms 超过上限」。
  - 超过 5 个时只显示前 5 个，加「查看全部 N 个」/「收起」。
- 内核未运行时第一行改为「内核未运行，监测已暂停」，按钮禁用。

### 3.2 节点页（ResourceCenter）

- 被监测的节点卡片右下角标记区显示铃铛图标 + 「监测」（主色）；不可用时显示静音铃铛 + 「不可用」（红色），tooltip「不可用 · 连续失败 N 次」/「监测中」。卡片已有标记（如 Tailscale 状态）时保留原标记，不显示监测标记。
- 卡片「⋯」菜单和右键菜单末尾加一项：未监测时「加入监测」，已监测时「移出监测」。
  - 加入：若监测关闭，则打开监测，范围设为「指定节点」，列表只有这个节点；若范围是「正在使用」，切到「指定节点」，列表 = 当前正在使用的节点 + 这个节点；若已是「指定节点」，追加。
  - 移出：范围切到（或保持）「指定节点」，列表 = 当前所有被监测节点逐个展开（整组展开成单个节点）后去掉这个节点。
- 只在节点页（ResourceCenter）的卡片上加；`NodeBrowser`（选择节点的对话框）里不加。

### 3.3 系统通知

Windows 原生 toast，应用名 Routa、Routa 图标。文案：

| 场景 | 标题 | 正文 |
|---|---|---|
| 单个节点变为不可用 | 节点不可用：{节点名} | 连续 {N} 次探测失败（{原因}）[ · 正在被「{使用者}」使用] |
| 同一轮有 ≥3 个节点新变为不可用 | {K} 个节点不可用 | {节点名1}、{节点名2}、…（最多列 5 个，超出加「等」） |
| 节点恢复 | 节点已恢复：{节点名} | 不可用约 {X} 分钟，当前延迟 {ms} ms |
| 疑似本机断网 | 网络可能不可用 | {N} 个监测节点同时探测失败，请检查本机网络。 |
| 本机网络恢复 | 网络已恢复 | 监测节点重新可以连通。 |

原因：`超时` / `连接失败` / `延迟 {ms} ms 超过上限`。时长 < 1 分钟显示「不到 1 分钟」，≥ 60 分钟显示「约 {h} 小时 {m} 分钟」。

**点击通知**：显示并聚焦主窗口（与单实例唤起同一逻辑），导航到节点页，滚动到该节点卡片并高亮约 3 秒（若节点所在分组折叠则展开）。合并通知定位到第一个节点；自动组出口的通知（没有节点卡片）打开代理页（`/listeners`）；「网络可能不可用」打开「设置 › 网络与内核」。窗口已关闭到托盘时同样适用。**只处理 Routa 进程还在运行时的点击**；Routa 退出后在通知中心点旧通知不做任何事（不注册 COM 激活或 `routa://` 协议，不改安装器）。

## 4. 判定规则

每轮探测（定时或「立即探测」）：

1. **前置条件**：监测开启、被监测节点非空、内核 Running 且最近一次 apply 为 `Reloaded`。不满足则跳过本轮，不改变任何节点状态，不计失败。
2. 对每个被监测节点并发测一次延迟（复用现有 `test_many`，测速 URL 用设置里的「测速 URL」，超时用现有默认值）。结果 `stale` 的（路径在测量期间变了）当作本轮没测，不计数。
3. 单个节点本轮**失败** = 无延迟（超时 / 连接失败）；或设了延迟上限且延迟 > 上限。`NoCore` / `CoreUnreachable` 表示内核出了问题：整轮作废，不改变任何状态。`NotFound` 只作废这一个 target（见第 5 节「出口未生效」），不影响其它 target。
4. **疑似断网**：本轮有效结果 ≥ 2 个且全部为「无延迟」（不含仅超延迟上限的），视为本机网络问题：节点计数和状态都不变；单独维护「网络连续失败次数」，达到阈值时发一次「网络可能不可用」，之后不再重复；之后第一个不是全部失败的轮次，若之前已发过断网通知且「恢复时通知」开启，发「网络已恢复」，然后计数清零，并按正常规则处理这一轮。只监测 1 个节点时没有断网判定。
5. 否则逐节点：失败则连续失败数 +1，达到阈值且之前不是不可用 → 变为不可用（记 down_since），加入「新不可用」列表；成功则连续失败数清零，之前不可用 → 变为可用，若「恢复时通知」开启则发恢复通知。
6. 新不可用 ≥3 个合并成一条通知，否则每个一条。
7. 被监测节点集合变化（改范围、改列表、节点被删、订阅更新删了节点）：移出集合的节点状态直接丢弃，不发通知；新加入的从「等待探测」开始。改了阈值不回溯：下一轮按新阈值判断。
8. 关闭监测：清空所有状态，不发通知。重新开启后立即探测一轮。

**探测时机**：开启监测、修改范围或间隔后，立即探测一轮；之后按间隔。因为最低间隔是 10 秒，不能复用现有 60 秒检查循环：监测用自己的循环（`tasks.rs` 里新增，检查粒度 ≤ 5 秒，或按下次到期时间 sleep 并在设置变化时唤醒，由实现者选）。**下一轮从上一轮结束时开始计时，同一时刻最多一轮在跑**，不会重叠。单次探测超时固定 5 秒（不用测速的 10 秒默认值），保证 10 秒间隔下一轮能在间隔内结束。Routa 启动后内核就绪即探测第一轮。系统睡眠唤醒后到期就探测，靠阈值吸收唤醒初期的网络抖动。

**与自动测速的关系**：两者独立运行，监测结果同样写入 DelayBook（卡片延迟随之更新）。

## 5.「正在使用的节点」怎么算

被引用的出口来自：`user_enabled` 的可见监听器的 `exit`，以及 `process_routing.enabled` 时 `user_enabled` 的进程分流规则所使用的（隐藏）出口。对每个被引用的出口：

- `Node { node }`：监测这个节点，探测时用该出口在 mihomo 里的代理名（这样会经过出口绑定的网卡，测的就是实际流量路径）。
- `Group { strategy: Select, selected: Some(n) }`：监测选中的节点，代理名用 `member_proxy_name`（同样经过出口网卡）。
- 其它 Group（UrlTest / Fallback / LoadBalance，或 Select 未选）：监测出口本身（显示名用出口名，次要信息写「自动选择 · {使用者}」）。组本身不可用（所有成员都挂了）时报警；单个成员挂了不报——那是组自己的事。
- `Direct`：不监测。

**按路径（代理名）去重，不按节点去重**：同一路径被多处使用只探测一次，「使用者」列出全部（逗号分隔，超长截断）；同一节点经不同网卡有多条路径时，是多个 target，各自计数、各自通知，label 为「{节点名} · 经 {网卡名}」（只有一条路径时不加后缀）。节点卡片上的监测标记取该节点所有 target 中最差的状态（任一 down → 「不可用」，tooltip 列出哪条路径）。

**出口未生效的 target**：出口健康状态不是 Ok 时不在 mihomo 配置里，探测会得到 `NotFound`。这只影响这一个 target：显示为灰点「出口未生效」，不计失败、不通知（出口问题已在代理页有提示），其它 target 照常探测。

**探测结果不改节点卡片的延迟**：「正在使用」按出口路径探测，写入 DelayBook 的 key 是出口 / 成员代理名，节点卡片（按节点自己的代理名读延迟）不会变；这是有意的，不双写。卡片上能看到的是监测标记。「指定节点」范围用节点自己的代理名，卡片延迟会随之更新。

「指定节点」范围：`MemberPicker` 的值展开为单个节点（整组按当前成员展开，订阅更新后自动跟随），用节点自己的代理名（`node_proxy_name` / `manual_proxy_name`）探测，不经过任何出口网卡。

## 6. 数据与接口

### 6.1 持久化（Model.settings，state.json）

在 `Settings` 里加一个带 `#[serde(default)]` 的 `node_monitor: NodeMonitorSettings`：

```rust
pub struct NodeMonitorSettings {
    pub enabled: bool,                 // false
    pub scope: MonitorScope,           // InUse
    pub members: Vec<ExitMember>,      // 指定节点时使用；InUse 时保留不清空
    pub interval_secs: u32,            // 300；取值 10/30/60/180/300/600/1800/3600，校验最低 10
    pub fail_threshold: u32,           // 2，1..=5
    pub latency_limit_ms: Option<u32>, // Some(1000)，1..=60000；None = 不限
    pub notify_recovery: bool,         // true
}
pub enum MonitorScope { InUse, Custom }
```

旧 state.json 没有该字段时取默认值。校验放在现有 `validate` 里（非法值拒绝保存并返回字段错误）。`members` 里引用到已删除节点的条目：保存时不报错，展开时跳过（与出口成员的「已失效」处理一致）。

保存走现有 `save_settings`；监测设置变化不触发 mihomo 重启 / 重新 apply。

### 6.2 运行时状态（RuntimeStatus，不持久化）

在 `RuntimeStatus` 加 `monitor: MonitorStatus`，随 `Status` 事件推送：

```rust
pub struct MonitorStatus {
    pub last_run: Option<i64>,
    pub next_run: Option<i64>,
    pub probing: bool,
    pub paused_reason: Option<MonitorPause>, // CoreNotRunning 等
    pub network_down: bool,
    pub targets: Vec<MonitorTarget>,         // 当前被监测集合，按显示顺序
}
pub struct MonitorTarget {
    pub proxy: String,         // 探测用代理名，也是 DelayBook 的 key
    pub node: Option<NodeRef>, // 对应节点；监测的是自动组出口时为 None
    pub label: String,         // 显示名
    pub used_by: Vec<String>,  // InUse 时的使用者
    pub fails: u32,
    pub down: bool,
    pub down_since: Option<i64>,
    pub last_ms: Option<u32>,
    pub last_failure: Option<MonitorFailure>, // Timeout / Failed / OverLimit(ms)
    pub probed: bool,
}
```

前端的节点卡片标记和 footer 列表都只读这里，不在前端自己展开范围。卡片和节点的对应用 `node`（`NodeRef`）比较。

### 6.3 命令

- `monitor_probe_now()`：立即探测一轮，返回后状态通过 Status 事件更新。
- 加入 / 移出监测：前端算出新的 `NodeMonitorSettings` 后走 `save_settings`，不新增命令。

### 6.4 通知

Windows toast 需要能收到点击回调，所以不用 `tauri-plugin-notification`（桌面端不支持点击回调），直接用 WinRT `ToastNotification`（`windows` crate 已在依赖中，需加 `UI_Notifications`、`Data_Xml_Dom` 等 feature），或 `tauri-winrt-notification` crate（支持 `on_activated`），由实现者选择。AppUserModelID 用安装包快捷方式上的 ID（与 `tauri.conf.json` 的 `identifier` 一致，需实现时确认 NSIS 包确实设置了）；开发构建拿不到时允许通知显示为其它来源，不阻塞功能。

点击回调里通过 launch 参数（如 `routa://node/{proxy}` 风格的字符串，具体格式由实现者定）在主进程里：显示并聚焦窗口，然后向前端发事件 `monitor-focus { target }`，前端导航并定位卡片。

通知发送失败（系统关闭了通知等）只记日志，不影响监测。

## 7. 其它约束与决定

1. 探测不能持有 engine 锁等待网络（参照 `test_delays` 的做法：拿快照后释放）。
2. 每轮最多探测的节点数不设上限，但用现有并发上限 `DEFAULT_CONCURRENCY`。
3. 简洁模式：不显示监测设置和卡片菜单项，但已开启的监测照常运行、照常通知。
4. 所有文案为中文；新增 UI 必须有 aria-label（与现有页面一致）。

## 8. 测试要点

- 判定规则（第 4 节）写成纯函数，单元测试覆盖：阈值、恢复、合并通知、断网判定与恢复、stale 结果、集合变化、阈值修改、关闭再开启。
- 「正在使用」展开（第 5 节）单元测试：Node 出口、Select 组、自动组、Direct、禁用的监听器、进程分流关闭、同一节点多处使用。
- 运行时：用现有 fake core 和暂停的 tokio 时钟测到期调度、内核未运行时跳过、设置变化后立即探测。
- 前端：设置分区的显示 / 隐藏、保存反馈、范围切换预填；节点卡片的菜单项和标记；`monitor-focus` 事件的导航与高亮。
- 通知本身做成 trait，测试里用记录器替代，断言发了哪些通知。

## 9. 我做的决定（请确认时一并检查）

- 默认值（用户已定：监测关闭、延迟上限 1000 ms、间隔最低 10 秒）：监测关闭；范围「正在使用的节点」；5 分钟；连续失败 2 次；延迟上限 1000 ms；恢复时通知开。
- 监测单次探测超时 5 秒；轮与轮不重叠，下一轮从上一轮结束起算。
- 断网判定：≥2 个节点且全部无延迟才算，只监测 1 个节点时不判定。
- 合并通知门槛：同一轮 ≥3 个。
- 自动选择的组（UrlTest / Fallback / LoadBalance）监测组本身，不监测成员。
- 「指定节点」不经过出口网卡；「正在使用」经过出口网卡。
- 简洁模式不显示监测 UI。
- 通知用 WinRT toast 而不是 `tauri-plugin-notification`，为了点击定位。
- 「正在使用」按路径去重（同节点经不同网卡 = 多个 target），卡片标记取最差状态。
- 出口未生效（`NotFound`）的 target 只显示「出口未生效」，不报警，不影响其它 target。
- 「正在使用」的探测结果不改节点卡片延迟。
- 换成「指定节点」时自动组出口被去掉并 Snackbar 提示；自动组的通知点击打开代理页。
- 点击通知只在 Routa 运行时生效，不做冷启动激活。
